# SCT 데이터 조회 / OCR 검수

두 화면으로 구성된 사내 웹앱입니다 (**로그인 필요**).

| 화면 | 경로 | 설명 |
|---|---|---|
| OCR 검수 | `/review` | 검수자가 이미지와 OCR 텍스트를 비교해 패스/타이핑 처리. 그리드에서 여러 건 일괄 패스 가능 |
| Admin 열람 | `/admin` | 검수 레코드 열람 + 참고용 코멘트 (**admin 계정만**). 의견이 하나라도 있으면 내용 공개 |

**`/`는 역할에 따라 갈립니다** — `role='admin'`이면 `/admin`, 그 외 계정은
`/review`입니다. admin은 검수 입력보다 열람이 주 업무라 열람 화면이 사실상 홈이고,
그래서 화면 간 이동 링크("Admin 열람" 탭)는 두지 않았습니다.

**admin은 `/review`에 들어갈 수 없습니다** — 직접 열어도 `/admin`으로 돌아갑니다
(2026-08-27). 역할 분기가 `/`에만 있던 동안에는 로그인 폼을 거치는 경로에서
admin이 검수 화면에 떨어졌습니다(로그아웃 상태의 `/` → `/review` →
`/login?next=/review` → 로그인 후 next를 따라 `/review`). 헤더만 "관리자 (admin)"이고
내용은 검수자 화면인 상태였고, 세션이 살아 있을 때는 `/`가 `/admin`으로 잘 가서
평소엔 드러나지 않았습니다. 진입 경로와 무관하게 막으려고 화면 자체에 가드를
뒀습니다. admin 담당자가 검수에도 참여하려면 **별도의 검수자 계정**을 쓰세요.

예전에 있던 **"SCT 데이터 조회"** 화면은 OCR 검수 화면과 역할이 거의 겹쳐서
없앴고, 고유 기능(`SCT 질문` 컬럼, `VLM 상태` 필터)만 검수 화면으로 옮겼습니다.
SCT 질문은 2026-08-26부터 **admin 화면에도** 나옵니다 — "OCR / 검수자 입력" 칸
맨 위, 검수자 카드와 같은 자리입니다(§4.5).

검수 워크플로우 사양은 `OCR 검수 시나리오.md`, 검수 DB 스키마는
`03_ocr_review_schema.sql`을 따릅니다.

같은 상위 폴더의 사내 대시보드 `Monitor/mielin_mon`(포트 8010)과 겹치지 않도록
**포트 8011**을 사용합니다. 스타일(패널/필터바/상태 뱃지/기간 프리셋 버튼)도
`mielin_mon`과 같은 톤으로 맞췄습니다.

## DB 구조

이 앱은 **서로 다른 두 DB**를 씁니다.

| 용도 | 설정 | DB | 권한 |
|---|---|---|---|
| SCT 원본 데이터 조회 | `MYSQL_*` | `mielin` @ `43.201.172.24` | SELECT 전용 |
| OCR 검수 의견 + 로그인 계정 | `REVIEW_MYSQL_*` | 로컬 `ocr_review` | 읽기/쓰기 |

`mielin`은 우리가 만든 게 아니라 시스템 관리자가 운영하는 별도 파이프라인이
채워주는 곳이며, `sct_import_records` 테이블 하나만 있습니다(우리 로컬 스키마와
거의 동일하되 `assessment_created_at` 컬럼이 하나 더 있음). 2026-04-15부터 오늘까지
데이터가 계속 갱신되고 있는 것을 확인했습니다.

두 DB는 서로 다른 서버일 수 있어 **SQL JOIN을 쓸 수 없습니다.** 그래서 검수
데이터는 `(assessment_id, drawing_id, answer_index)` 자연 키로만 원본을
논리적으로 참조하고, 두 쪽을 합치는 일은 애플리케이션 레이어에서 합니다
(`app/main.py`의 admin 열람 / 미검토 필터).

로컬 MySQL(`.mysql/`)에는 개발 초기 백필 테스트용 `sct_local` DB도 남아 있지만
웹앱은 더 이상 사용하지 않습니다. 지금 쓰는 건 `ocr_review` 쪽입니다.

## 실행 방법

검수 화면과 **로그인**은 검수 DB(`ocr_review`)를 쓰므로 로컬 MySQL이 떠 있어야
합니다 — 계정이 이 DB에 있기 때문에, 꺼져 있으면 로그인 자체가 안 됩니다.

Windows 서비스로 등록하지 않았으므로(관리자 권한 필요) 재부팅하면 MySQL이
자동으로 뜨지 않습니다. 아래처럼 수동으로 띄웁니다.

```powershell
# 1. 로컬 MySQL 기동
Start-Process -FilePath "C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqld.exe" `
  -ArgumentList '--defaults-file="C:\Users\chy22\Mielin\mielin_SCT\.mysql\my.ini"' -WindowStyle Hidden

# 2. 앱 실행 (터미널 포그라운드로 두세요)
uv sync
uv run watchfiles 'uvicorn app.main:app --host 127.0.0.1 --port 8011' app
```

브라우저에서 http://127.0.0.1:8011 접속 → 로그인 화면으로 이동합니다.

### `--reload` 대신 watchfiles 를 쓰는 이유 (2026-08-27)

`uvicorn --reload`는 **이 환경에서 코드 수정이 반영되지 않습니다.** uvicorn의
Windows 리로더는 옛 워커에게 `os.kill(pid, CTRL_C_EVENT)`를 보내고
`process.join()`으로 기다리는데, Windows에서 `CTRL_C_EVENT`는 **프로세스 그룹
리더에게만** 전달됩니다. uvicorn 워커는 평범한 `spawn.Process`라 그룹 리더가
아니므로 이 호출은 에러 없이 성공하고 **신호는 도달하지 않습니다** (같은 방식으로
재현한 실험에서 자식이 150초 뒤에도 생존했습니다). 리로더는 `join()`에서 막히고
옛 워커가 옛 코드로 계속 응답합니다.

실측한 반영 시간: `--reload`는 1초 / 12초 / 26초 / 45초 / 84초 / 100초 초과(미반영)로
들쭉날쭉하고, 한 번 막히면 그 뒤 수정은 감지조차 되지 않습니다. watchfiles로
감싸면 1.6초로 일관됩니다. 6줄짜리 FastAPI 앱에서도 같은 증상이 재현되므로 이
프로젝트 코드와는 무관합니다.

HTML·JS·CSS는 요청마다 디스크에서 읽어 넘기므로(`FileResponse`/`StaticFiles`)
리로드와 무관하게 항상 즉시 반영됩니다. 그래서 "가끔만 반영이 안 된다"로
보였지만, 실제로 불안정한 것은 `.py` 수정뿐이었습니다.

바뀌는 점 두 가지만 알아두면 됩니다.

- 감시 대상이 `app/` 폴더의 **모든 확장자**입니다 — `.py`뿐 아니라 HTML·JS·CSS·`.env`
  수정에도 재시작합니다(1.6초). `.py`만 보게 하려면 `--filter python`을 붙이고,
  `scripts/` 등 다른 폴더까지 보려면 `... app scripts`처럼 경로를 더 줍니다.
- 재시작이 강제 종료입니다(Windows에서 `os.kill(SIGINT)`은 `TerminateProcess`로
  동작). 그 순간 처리 중이던 요청은 끊깁니다. 이 앱에는 shutdown 훅이 없어
  잃을 정리 작업은 없습니다.

**PowerShell에서 `*>`로 로그 파일에 넘기지 마세요** — PowerShell 5.1이 UTF-16으로
쓰고 네이티브 stderr를 ErrorRecord로 감싸 로그가 깨집니다. 백그라운드로 돌리면서
로그를 남기려면 `cmd`를 거칩니다.

```powershell
# 백그라운드 실행 + 로그 남기기
Start-Process cmd -ArgumentList '/c','uv run watchfiles "uvicorn app.main:app --host 127.0.0.1 --port 8011" app > uvicorn_out.log 2>&1' -WorkingDirectory "C:\Users\chy22\Mielin\mielin_SCT" -WindowStyle Hidden
```

MySQL 중지:

```powershell
& "C:\Program Files\MySQL\MySQL Server 8.4\bin\mysqladmin.exe" -u root -p shutdown
```

> **root 비밀번호는 `.mysql/credentials.txt`에 있습니다** (gitignore 대상).
> 앱 계정 `sct_app`의 비밀번호와 다릅니다 — 마이그레이션·데이터 삭제 등
> 관리 작업에는 root가 필요합니다.

### 최초 1회 (DB 준비)

```powershell

# username 컬럼 추가 (03을 이미 적용한 기존 DB일 때만 — 여러 번 실행해도 안전)

# 수정 이력 테이블 (기존 DB일 때만 — 여러 번 실행해도 안전)

# admin 참고 코멘트에 분류 추가 (기존 DB일 때만 — 13에서 제거되므로 새 DB는 생략 가능)
mysql --default-character-set=utf8mb4 -u root -p ocr_review < 06_add_admin_comment_classification.sql

# admin 코멘트 1건/수정 가능으로 변경 (기존 DB일 때만 — 여러 번 실행해도 안전)

mysql --default-character-set=utf8mb4 -u root -p ocr_review < 08_add_review_difficulty_level.sql

# 부정 표현 자동 감지 (기존 DB일 때만 — 여러 번 실행해도 안전, §5.2)

# OCR 텍스트 스냅샷 + 차이 자동 기록 (기존 DB일 때만 — 여러 번 실행해도 안전, §5.3)
mysql --default-character-set=utf8mb4 -u root -p ocr_review < 10_add_ocr_diff.sql

# 띄어쓰기 차이 분리 (기존 DB일 때만 — 여러 번 실행해도 안전, §5.3)

uv run python -m scripts.seed_reviewers
```

> ⚠️ **`--default-character-set=utf8mb4`를 빼먹지 마세요.** Windows의 mysql CLI는
> 기본 문자셋이 utf8mb4가 아니라서, 옵션 없이 실행하면 분류 라벨(한글) INSERT가
> `ERROR 1366 Incorrect string value`로 실패합니다. (다행히 깨진 값이 저장되는 게
> 아니라 아예 거부되므로, 기존 데이터가 손상되지는 않습니다.)

마이그레이션은 `ALTER` 권한이 필요해 **root로 실행**해야 합니다 — 앱 계정
`sct_app`은 SELECT/INSERT/UPDATE만 갖고 있습니다. **DELETE도 없습니다**(검수
기록은 append-only) — 의도된 제한이라 그대로 두고, 데이터를 지워야 하면 root로
하세요. 이미 있는 계정의 비밀번호까지 다시 덮어쓰려면 `--reset-password`를 붙이세요.

## 로그인 / 계정

로그인 계정은 검수 DB의 **`ocr_reviewers` 테이블**이 소스입니다. 별도 계정
목록을 `.env`에 두지 않는 이유는, 검수 의견(`ocr_review_comments.reviewer_id`)과
admin 코멘트(`ocr_admin_comments.admin_id`)가 이미 이 테이블을 FK로 참조하고
있어서 로그인 계정을 따로 두면 "로그인한 사람"과 "의견을 남긴 사람"의 매핑을
이중으로 관리해야 하기 때문입니다. 세션에 `reviewer_id`를 담아두면 그 매핑이
아예 필요 없어집니다.

| 아이디 | 역할 | 비고 |
|---|---|---|
| `technonia01` | annotator | 검수자 A |
| `technonia02` | annotator | 검수자 B |
| `admin` | admin | Admin 열람 화면 접근 가능 |

- 비밀번호는 **bcrypt 해시로만** 저장됩니다 (평문 저장 없음).
- `role='admin'`이 아닌 계정은 `/admin`과 `/api/ocr/admin/*`에서 403을 받습니다.
  반대로 `role='admin'` 계정은 `/review`에서 `/admin`으로 리다이렉트됩니다.
  로그인 후 도착하는 화면도 역할에 따라 갈립니다(위 표 참고).
- 계정을 추가하려면 `scripts/seed_reviewers.py`의 `ACCOUNTS`에 한 줄 추가한 뒤
  다시 실행하면 됩니다.
- 로그인 아이디는 `email`이 아니라 `username` 컬럼입니다 — 실제 계정이 이메일
  형식이 아니라서 `04_add_reviewer_username.sql`로 분리했습니다.

## 검수 처리량 (전수 검사)

전수 검사가 목표이고 대상이 **44,823건**(하루 약 520건씩 유입)입니다. 완료 조건이
"독립된 2명"이라 총 약 90,000 처리 건이 필요합니다.

그래서 검수 화면은 **그리드 카드 격자**를 씁니다. OCR 평균 길이가 8.5자
(3자 이하가 23%)라 대부분의 판단은 1~2초면 끝나는데, 한 건씩 크게 띄우면 스크롤과
클릭이 판단보다 오래 걸립니다.

패스 경로는 **체크박스 + [제출]** 하나로 통일했습니다.

| 하고 싶은 것 | 조작 |
|---|---|
| 한 건만 패스 | 그 카드의 난이도(1~4)를 고르고 **체크한 뒤 [제출]** |
| 여러 건 한 번에 패스 | 카드마다 난이도를 고르고 여러 개 체크 → 하단 고정 바의 일괄 패스 |
| 타이핑 | 체크하지 **않고** 텍스트를 입력해 [제출] |

카드마다 별도 [패스] 버튼을 뒀던 적이 있지만, 그 버튼이 체크 상태를 무시하는
두 번째 진입점이 되어 혼란스러워서 없앴습니다.

판독이 어려운 건은 이미지를 클릭하면 원본 크기 모달이 열립니다 — 예전엔 이를 위한
별도 **리스트 모드**가 있었지만, 모달이 같은 역할을 해서 2026-08-21에 없앴습니다
(그리드 하나로 통일).

카드 크기는 **1920×1080에서 한 줄에 4장**이 들어가도록 잡았습니다(2026-08-24).
그전에는 5장이었는데 OCR 텍스트와 난이도 버튼이 너무 작아 읽기 어려웠습니다 —
카드를 키운 만큼 안쪽 글씨와 버튼도 같이 키웠습니다.

⚠️ 일괄 패스에는 **"전체 선택" 버튼이 의도적으로 없습니다.** 이미지를 보지 않고
한꺼번에 넘기면 검수 데이터 자체가 무의미해지기 때문입니다. 1회 상한은 50건입니다.

카드의 패스 체크박스는 **목록을 불러올 때 기본으로 켜진 채로 그려집니다**
(2026-08-31) — 대부분 OCR이 그대로 맞아서 매번 체크하는 반복 클릭을 줄였습니다.
"전체 선택" 버튼과는 다릅니다: 난이도는 여전히 카드마다 직접 골라야만 제출되므로,
안 맞는 건은 타이핑을 시작하는 순간 그 카드의 체크가 자동으로 풀립니다. **판독
불가 버튼도 같은 방식으로 체크를 끕니다** (같은 날 후속 수정) — 처음엔 타이핑
쪽에만 이 처리가 있어서, 체크된 채로 판독 불가를 고르고 제출하면 "판독 불가는
패스로 처리할 수 없습니다" 에러가 매번 났습니다.

### 검수 대상에서 제외되는 레코드

**이미지가 없는 1,353건(전체의 3%)은 검수 목록에 나오지 않습니다.** 이 레코드들은
`s3_key`·`media_id`·`vlm_status`·`ocr_text`가 **모두 함께 NULL**입니다(건수가 정확히
일치). 업로드된 이미지가 애초에 없어서 VLM도 돌지 않은 빈 레코드라 검수할 대상이
없습니다. 화면은 `has_image=true`를 항상 붙여 이들을 걸러냅니다.

이 레코드들은 연속 블록으로 뭉쳐 있어서(한 검사 단위로 통째로 없는 듯), 걸러내지
않으면 첫 페이지가 온통 "이미지 준비 중"으로 보입니다. 참고로 `s3_key`가 있는
43,470건은 S3에서 정상 조회되는 것을 확인했습니다 — 표시 실패 케이스는 없습니다.

### 내 처리 상태 필터

검수 화면 상단 드롭다운으로 고릅니다.

| 값 | 의미 |
|---|---|
| 내가 아직 처리하지 않은 것 *(기본)* | 내 처리 기록이 없는 레코드 |
| 내가 타이핑한 것 | 내가 `transcription`으로 남긴 것만 |
| 내가 패스한 것 | 내가 `normal_check`로 남긴 것만 |
| 전체 | 처리 여부 무관 |

완료 전(두 번째 검수자 미도착)이라도 **본인이 남긴 내용은 화면에 표시됩니다** —
블라인드는 "남의 의견"을 가리는 규칙이고, 내 입력을 내가 확인하는 건 무관합니다.

### 판독 불가 제외 / 난이도 필터 (2026-08-24)

난이도와 판독 불가는 **한 팝오버 안에서 함께** 고릅니다. 접힌 버튼이 곧 현재
설정입니다(`판독 불가 제외` / `난이도 1,2 · 판독불가 제외` / `판독 불가만`).

```
[판독 불가 제외 ▾]
  난이도      [1] [2] [3] [4]
  ─────────────────────────
  판독 불가   [제외] [포함] [만 보기]
  ─────────────────────────
  기본값으로 되돌리기
```

**판독 불가는 이 3단 선택 하나만 담당합니다** — 난이도 등급(1~4)과 별개 판정이라
5번 버튼으로 두지 않습니다. 예전에 체크박스와 난이도 5번이 같은 대상을 각각
조작해 `제외 ✓ + 난이도 5 = 0건`이라는 모순 조합이 있었습니다.

| 조합 (검수자 A 기준) | 결과 |
|---|---|
| 타이핑한 것 + 제외 *(기본)* | **7건** (실제 타이핑만) |
| 타이핑한 것 + 포함 | **22건** (판독 불가 15건 포함) |
| 타이핑한 것 + 만 보기 | **15건** |
| 아직 처리하지 않은 것 | 3단 선택·난이도와 **무관하게 47,004건** |

**난이도 필터의 기본값은 항상 "전체 난이도(1~5) = 필터 미적용"입니다.** 예전에는
판독 불가를 빼려고 기본을 1~4로 뒀는데, 난이도가 없는 미처리 건이 전부 걸러져
기본 작업 화면이 비어버렸습니다. 판독 불가 제외를 체크박스로 분리하면서 난이도는
"등급으로 좁혀보기"라는 본래 역할만 하게 됐고, **어떤 처리 상태에서도 기본값이
달라지지 않습니다.**

⚠️ **아직 처리하지 않은 것**에서는 난이도가 **완전히 무시됩니다** — 미처리 건에는
난이도 자체가 없어서, 적용하면 항상 0건이 되기 때문입니다.

### 검수자 화면의 "부정 표현만" 필터 (2026-08-24 재정의, 라벨은 2026-08-31 정정)

라벨은 한동안 "부정 표현 포함"이었지만, 실제 동작은 처음부터 "부정 표현이 있는
것만" 골라내는 배타적 필터였습니다 — 이름이 실제 동작과 맞지 않아 2026-08-31에
"부정 표현만"으로 되돌렸습니다(admin 화면도 동일). 로직은 바뀌지 않았습니다.

두 기준을 **OR로 합쳐** 거릅니다:

1. **내가 부정 표현으로 확정한 것** (체크박스를 켠 채 제출)
2. **아직 내가 처리하지 않았고** OCR 텍스트에 키워드가 있는 것

처리 후에는 **사람의 판단이 자동 감지를 이깁니다** — 키워드가 없는 답변에 직접
체크하면 잡히고, 자동 감지된 것을 해제하면 사라집니다. 처리 전에는 키워드로
"위험한 답변을 미리 훑어보는" 용도가 그대로 유지됩니다.

> 예전에는 (2)만 봤습니다. 그래서 직접 체크해도 안 잡히고 해제해도 계속 잡혀,
> 같은 이름의 admin 필터와 서로 다른 답을 냈습니다(검수자 372건 vs admin 1건).
> 한쪽 기준만 쓰지 않은 이유는, 미처리 레코드에는 아직 판단 자체가 없어서
> 판단 기준만으로는 미리 볼 수 없기 때문입니다.

### Admin 열람 필터 (2026-08-24 재구성)

**배타적인 상태는 드롭다운**, **부정 표현은 독립 체크박스**로 나눠뒀습니다.
부정 표현은 타이핑/패스 어느 쪽과도 같이 걸릴 수 있는 별개 속성이라, 드롭다운에
끼워 넣으면 "타이핑 + 부정 표현" 같은 조회가 막히기 때문입니다. 검수자 화면도
같은 구조입니다.

목록에서 부정 표현은 **출처를 구분해 표시**합니다 (2026-08-24):

| 표시 | 뜻 |
|---|---|
| ⚠ 부정 표현 **(자동감지)** | 시스템이 키워드로 감지했고, 검수자가 그대로 확정 |
| ⚠ 부정 표현 **(검수자 판단)** | 자동 감지는 안 됐지만 검수자가 직접 체크 |
| *(표시 없음)* | 검수자가 체크하지 않음 — **자동 감지됐더라도 해제했으면 표시하지 않습니다** |

마지막 줄이 중요합니다. 부정 표현 단어가 들어 있다고 해서 모두 부정 표현인 것은
아니므로(예: 소설 인용), 최종 판단은 사람의 것을 따릅니다. 자동 감지 여부는
저장돼 있지 않아 서버가 **검수 당시 OCR 스냅샷으로 다시 계산**합니다 — 지금의 OCR
텍스트로 계산하면 그 사이 OCR이 갱신된 경우 당시와 다른 답이 나오기 때문입니다.

| 드롭다운 값 | 의미 |
|---|---|
| 타이핑한 것 *(기본)* | 한 명이라도 **텍스트를 실제로 옮겨 적은** 레코드 (판독 불가 제외) |
| OCR 텍스트와 다른 것 | 한 명이라도 OCR과 실제로 다르게 입력한 것 (`ocr_diff_char_count > 0`) |
| 판독 불가 | 한 명이라도 판독 불가로 판정한 레코드 |
| 패스한 것 | **타이핑도 판독 불가도 한 명 없는** 레코드 — 둘 다 패스했거나, 한 명만 패스하고 나머지는 미처리인 경우까지 포함 |
| 전체 (처리 여부 무관) | 필터 없음 |

여기에 난이도·연령대·VLM 모델·검수자·완료 여부·기간 필터를 자유롭게 조합합니다.
(**연령대·VLM 모델은 admin 화면에만** 있습니다 — 검수자는 이미지를 보고 판정만
하므로 모델·연령대로 나눠 작업할 이유가 없어 2026-08-24에 검수자 화면에서 뺐습니다.)

**"완료 여부" 드롭다운** (전체 / 완료(2명) / 진행중(1명), 2026-08-31 신설)은
"검수자" 필터와 별개 축입니다 — 하나는 "누가"(신원), 하나는 "몇 명이"(개수)를
묻는 서로 다른 질문이라 독립된 컨트롤로 두고 AND로 조합됩니다. 예: 검수자 A +
완료(2명)를 함께 고르면 "A가 참여했고 이미 완료된 건"만 남습니다. 서버
파라미터(`status`)는 원래부터 있었고 화면 컨트롤만 새로 추가했습니다.

**난이도는 여러 개를 동시에 고를 수 있습니다** (2026-08-24). `전체 난이도 ▾`를
누르면 알약 버튼 `[1][2][3][4][5]`가 펼쳐지고, 원하는 것만 켜면 됩니다
("1,2,3,4를 한꺼번에" / "1,2만"). 접힌 버튼이 선택 상태를 그대로 보여줍니다
(`난이도 1, 2` / 3개 이상이면 `난이도 3개 선택`). 검수자 화면도 같은 위젯입니다.

⚠️ **아무것도 안 고른 상태 = 전체**이며, 이는 `1~5를 모두 켠 것과 다릅니다`.
모두 켜면 난이도가 없는 과거 데이터(난이도 도입 이전)가 조용히 빠집니다.
**검수자를 특정하면 드롭다운의 의미가 좁혀집니다** — "누구든 한 명이라도"가
"그 검수자 본인이"로 바뀝니다.

**판독 불가는 타이핑과 분리해서 봅니다** (2026-08-24). DB에는 둘 다
`review_type='transcription'`이지만 "읽을 수 없어 판정을 못 했다"와 "OCR이 틀려서
다시 적었다"는 분석상 정반대 의미입니다. 판정 기준은 난이도 5가 아니라
**"transcription인데 옮겨 적은 텍스트가 없다"** 입니다 — 텍스트 없이 난이도 1~4를
낸 제출은 서버가 패스로 재분류하므로 이 조건이 구조적으로 성립하고, 난이도 도입
이전의 레거시 데이터까지 함께 잡힙니다. 덕분에 **타이핑한 것 / 판독 불가 /
패스한 것이 레코드 전체를 빠짐없이 나눕니다.**

상단 **진행 현황 카드**는 검수자 수 + 4개입니다 (2026-08-24 재구성, 진행중 카드는
2026-08-31에 검수자별로 분리):

| 카드 | 세는 대상 |
|---|---|
| 전체 SCT 검사 수 | `assessment_id` 고유값 |
| 전체 검사자 수 | `client_id` 고유값 |
| **전체 이미지 수** | `s3_key`가 있는 레코드 — 목록의 `has_image` 필터와 같은 기준 |
| 검수 완료 (2명 이상) | 의견이 2건 이상인 레코드 |
| 진행중 · 검수자별 (검수자 수만큼) | 의견이 정확히 1건이고, 그 1건의 작성자가 이 검수자인 레코드. "1명만 처리" 총합 하나 대신, 어느 검수자가 밀리고 있는지 바로 보이도록 나눴습니다. 현역 검수자 수만큼 카드가 자동으로 생깁니다 — 지금은 검수자 A/B 2장 |

**패스도 "처리한 것"으로 셉니다.** 예전에는 타이핑이 없는 레코드를 빼서 실제보다
작게 나왔는데(진행중 25 vs 실제 97), 검수자가 이미지를 보고 "OCR이 맞다"고 판정한
것도 처리한 것입니다. 이제 `완료 + 진행중`이 목록의 전체 건수와 정확히 맞습니다.

⚠️ **아직 아무도 처리하지 않은 레코드는 이 화면에 나오지 않습니다** — "전체"를
골라도 마찬가지입니다. 목록의 출발점이 `v_sct_review_status`(의견이 1건 이상 있는
레코드)이기 때문이고, 의도된 동작입니다. 미처리 건을 찾아 처리하는 건 검수자
화면의 역할이고, admin 화면은 "남겨진 의견을 확인하는" 곳입니다.

### 검수 의견 수정 (패스·타이핑 공통, 2026-08-21부터)

본인이 남긴 의견은 카드/행의 파란 영역에서 **[수정]** 으로 고칠 수 있습니다
(완료된 건도, **패스도** 가능 — 처음엔 타이핑만 가능했지만 "난이도를 잘못
골랐는데 못 고침" 문제로 패스까지 넓어졌습니다). 시나리오 §1이 "의견을 수정
없이 보존"을 최우선으로 두므로, 다음 제약이 서버에서 강제됩니다.

| 규칙 | 동작 |
|---|---|
| 본인 것만 수정 | 남의 의견 수정 시도 → **403** |
| 난이도(1~5)는 항상 필수 | 없으면 → **400** |
| 판독 불가(5) + 텍스트 동시 불가 | → **400** (모순 조합) |
| 원본 보존 | 수정 직전 값이 `ocr_review_edits`에 append (append-only) |
| 완료 후 수정 표시 | `was_completed = 1`로 기록 + 화면에 경고 |

**`review_type`은 저장된 값이 아니라 매번 다시 계산됩니다** — 텍스트를 채워
저장하면 그 순간 타이핑으로 분류되어 "패스" 표시가 사라지고, 텍스트를 비우고
난이도 1~4를 남기면 패스로 분류됩니다. **양방향으로 자유롭게 전환됩니다** —
패스↔타이핑 어느 쪽으로 고쳐도 최초 값은 `ocr_review_edits`에 그대로 남아
처음 판단이 무엇이었는지 사라지지 않습니다. 판독 불가(5)는 텍스트가 있으면
안 되므로, 텍스트를 비우고 5를 고르면 판독 불가로 전환됩니다.

**완료 후 수정 위험은 이제 대부분 해소됐습니다.** 완료 후에도 **상대방 의견
내용 자체는 절대 공개되지 않고**(2026-08-21, 아래 블라인드 항목 참고),
**"이미 완료됐다"는 사실조차 검수자 화면에서 알 수 없습니다** — "완료" 배지에
숫자(n/2)를 빼서, 본인이 몇 번째로 처리했든 상대 진행 상황을 전혀 알 수
없게 했습니다. 그래도 `was_completed = 1`은 DB에 계속 기록되며, §6에서
데이터를 뽑을 때는 여전히 구분해서 취급하는 것을 권장합니다 — "그 시점에
뭔가를 알고 고쳤다"는 뜻은 아니지만, "상대방 제출 이후에 일어난 수정"이라는
타이밍 정보 자체는 분석에 참고할 수 있기 때문입니다.

수정해도 별도 안내 문구는 뜨지 않습니다(화면에서 값이 바로 바뀌는 게 보이므로
불필요) — 대신 **`수정 2회`처럼 횟수만 표시됩니다** (2026-08-24). 이전에 입력했던
내용 자체는 저장하지도 보여주지도 않습니다: 최종 검수 결과를 얻는 것이 목표이고,
빠르게 입력하다 생긴 오타를 고친 기록은 그 목표에 기여하지 않기 때문입니다.
횟수를 남기는 이유는 **여러 번 고쳤다는 사실이 "검수 기준이 안 잡혔다"는 관리
신호**라서입니다. 완료 후 수정이 있었으면 `· 완료 후 수정 포함`이 함께 붙습니다.
**본인 것만** 보입니다 — 상대 검수자의 의견/수정 정보는 완료 여부와 무관하게
검수자 화면에 전혀 노출되지 않습니다. 두 검수자를 나란히 비교하는 건 admin
화면만의 역할입니다.

## 검수 워크플로우에서 중요한 규칙

`OCR 검수 시나리오.md`의 핵심 원칙 중 **코드로 강제되고 있는 것**들입니다.

- **블라인드 (§1/§3/§4.3/§4.4)** — 다른 검수자의 의견 내용은 **제출 전이든
  완료 후든 항상** 서버 응답에 담기지 않습니다 (`app/main.py`의 `_blind_state`,
  2026-08-21부터 완료 후에도 강제). **처리 여부 자체**(원래 `review_count`/
  `status` 필드로 내려주던 "상대가 몇 명 처리했는지")도 이제 아예 응답에서
  뺐습니다 — 검수자 화면은 상대 진행 상황을 몰라도 되는 독립 운영 화면이기
  때문입니다(같은 날 추가 변경). 화면에서만 가리면 개발자도구로 그대로
  보이므로 서버에서 막습니다. admin 화면은 이 함수를 쓰지 않는 별도
  엔드포인트라 무관하며, 진행 현황 집계는 계속 admin 화면의 역할입니다.
- **신원 (§4.3)** — `reviewer_id`/`admin_id`는 클라이언트가 보내지 않습니다.
  세션에서 채우므로 남의 이름으로 의견을 남길 수 없습니다.
- **중복 방지 (§4.3)** — `uq_review_per_reviewer` 유니크 제약. 위반 시 409.
  (존재하지 않는 검수자 등 FK 위반은 400으로 구분해서 내려줍니다.)
- **완료 판정 (§4.4)** — 독립된 검수자 2명이 처리하면 즉시 `completed`.
  admin 코멘트는 완료 상태에 영향을 주지 않습니다.
- **admin 열람 범위 (§4.5)** — **의견이 하나라도 등록되면 내용을 공개합니다**
  (완료 여부 무관). admin도 검수자로 참여할 수 있어서(§2) 이론상 독립성이 깨질
  수 있지만, 소수 인력으로 전수 검사를 진행하는 현재 운영 방식상 admin이 진행
  상황을 빠르게 파악하는 쪽을 우선했습니다.
- **원본 불변 (§4.5)** — admin은 결정권자가 아니며 검수자 원본을 수정하지
  않습니다. 코멘트는 `ocr_admin_comments`에 별도 보존됩니다.
- **admin 판정 (난이도 + 코멘트, 2026-08-24 개편)** — `[판정 입력]` 버튼을 누르면
  **모달**이 열리고, 난이도(1~4 + 판독 불가)와 코멘트를 남길 수 있습니다
  (`ocr_admin_comments.difficulty_level`, `12_add_admin_comment_difficulty.sql`).
  난이도는 **두 검수자가 다른 값을 냈을 때의 중재값**입니다 — 관리자는 두 의견을
  모두 본 뒤 판단하는 **비블라인드 판정**이라 검수자 난이도와 별개 컬럼에 담고,
  목록에는 `난이도: 5 (판독 불가) · 확정`처럼 **`확정`을 붙여** 구분합니다.
  완료 판정이나 검수자 의견에는 영향을 주지 않습니다.
  코멘트는 **선택**이며(난이도만 남겨도 됨) 둘 다 비면 400으로 막습니다.
  admin당 레코드당 1건이고(`uq_admin_comment_per_admin`), 본인 것만 수정할 수
  있습니다 (`PATCH /api/ocr/admin/comments/{id}` — 남의 것은 403).

  > 분류(classification) 체계는 2026-08-24에 **완전히 제거**했습니다
  > (`13_drop_classification.sql`) — 검수자 쪽은 난이도로 대체된 지 오래고
  > admin 코멘트까지 난이도로 바뀌면서 어느 화면에서도 쓰이지 않게 됐습니다.

## 환경 변수 (`app/.env`)

`app/.env.template`을 참고하세요. 주요 항목:

- `MYSQL_*` — **SCT 원본 조회용 목적지 DB.** 지금은 `mielin` 웨어하우스 DB
  (`43.201.172.24`, 계정 `admin`)를 가리킵니다. 웹앱은 `SELECT`만 실행합니다
  (`app/mysql_reader.py`가 코드 레벨에서도 SELECT 외 쿼리를 막음).
- `REVIEW_MYSQL_*` — **검수 DB (`ocr_review`).** 검수 의견 쓰기와 로그인 계정
  조회에 씁니다. 비어 있으면 검수/로그인 관련 API가 503을 반환합니다.
  계정(`sct_app`)에는 SELECT/INSERT/UPDATE만 있고 **DELETE는 없습니다** —
  검수 기록은 append-only이므로 의도된 제한입니다.
- `SESSION_SECRET_KEY` — 세션 쿠키 서명 키. 비어 있으면 앱이 기동하지 않습니다.
  `python -c "import secrets; print(secrets.token_hex(32))"`로 생성하세요.
  **이 값을 바꾸면 기존 로그인 세션이 전부 만료됩니다.**
- `SEED_REVIEWER_PASSWORD` — `scripts/seed_reviewers.py`가 계정을 시딩할 때만
  쓰는 값입니다. 로그인 검증에는 쓰이지 않습니다(검증은 DB의 해시로 함).
- `SESSION_MAX_AGE_SECONDS` — 세션 유효시간 (기본 12시간).
- `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_REGION` / `S3_BUCKET`
  — SCT 이미지는 S3(`cmaps-hub`, `ap-northeast-2`)에 있습니다. 값이 비어 있으면
  이미지 셀은 "이미지 준비 중" 플레이스홀더로 표시되고 앱은 정상 동작합니다.

## 알려진 제한 사항 / 다음 단계

- **성능 (시나리오 §7)** — "내가 아직 처리하지 않은 것" 필터는 검수 DB에서 내
  처리 키를 최대 20,000건 가져와 `mielin` 쿼리에서 `NOT IN`으로 제외하는
  방식입니다. 상한을 넘으면 응답에 경고를 실어 보내지만(조용히 틀리지 않도록),
  데이터가 그 규모에 도달하면 별도 상태 테이블로 옮겨야 합니다.
- **admin 목록 스캔이 조용히 잘립니다** — admin 화면은 `v_sct_review_status`를
  1,000건 상한으로 스캔하는데, **검수자 화면과 달리 잘렸다는 경고가 없습니다.**
  상한을 넘으면 오래된 레코드가 말없이 빠집니다. 현재 91건이라 당장 문제는
  없지만, 늘어나기 전에 경고를 붙이거나 스캔을 페이지네이션해야 합니다.
- **일치/불일치 판정 기준 (구현 제거됨, 결정은 미완)** — 서버가 계산해 응답에
  담던 `mismatch` 값과 `?mismatch=` 필터를 **2026-08-27에 제거했습니다.** 기준이
  **난이도값 비교 + 패스는 전부 일치**여서 "둘 다 패스인데 난이도가 2 vs 1"인
  건을 놓쳤고(실제 데이터에서 불일치 3건 중 1건만 잡힘), 2026-08-19부터 화면
  노출이 보류돼 **어느 화면도 쓰지 않는 틀린 계산**만 남아 있었기 때문입니다.
  완료 레코드는 계속 "완료 (n/2)"로만 표시합니다. 기준을 정해 다시 만드는 일은
  관리자 중재 대기열과 함께 남아 있습니다. **확인 필요 (§7).**
- **난이도 선택 시점** — 시나리오 §4.4는 "2명 모두 처리 완료 시 → 이어서 선택"으로
  읽히지만, 구현은 제출 시점에 받습니다. "내가 얼마나 어렵게 느꼈는가"는 상대방
  결과가 필요 없는 본인만의 판단이고, 제출 시점에 받는 편이 블라인드 원칙에 더
  안전해서 그렇게 했습니다. **확인 필요.**
- 병원명은 아직 표시하지 못하고 `hospital_id` 숫자만 표시합니다(스키마에 병원명
  매핑 테이블이 없음).
- **`ocr_failed` 컬럼은 44,823건 전부 0**이라 필터로 쓸 수 없습니다. 예전 조회
  화면의 "OCR 실패" 필터가 무용지물이었던 이유이고, 그래서 통합할 때 옮기지
  않았습니다. `sct_na_reason`도 전 레코드 NULL입니다.
- 이미지 요청(`/api/sct/records/{id}/image`)은 건당 원격 DB 조회 1회를 하고,
  `MysqlReader`가 커넥션 하나를 락으로 직렬화합니다. 실측상 요청당 약 15ms씩
  계단식으로 밀립니다(24장 = 약 360ms). 지금은 체감 문제가 없지만, 목록 응답에
  프리사인 URL을 함께 내려 브라우저가 S3로 직접 가게 하면 이 왕복을 없앨 수
  있습니다.
- `mielin` DB를 채우는 파이프라인의 정체(누가 관리하는지, 어떤 주기로 도는지)를
  아직 파악 중입니다 — 가끔 최신 날짜를 확인하는 게 좋습니다.
- 웹앱은 공유 DB(`mielin`)에 `SELECT`만 하도록 코드/역할을 제한해뒀지만, 그 DB
  자체를 우리가 소유/관리하는 게 아니므로 스키마가 바뀔 경우 영향을 받을 수 있습니다.
- **admin 계정 관리 (시나리오 §7)** — 계정 등록은 `scripts/seed_reviewers.py`
  수동 실행 방식입니다. 웹 UI에서의 계정 관리 화면은 아직 없습니다.
